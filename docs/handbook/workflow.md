# 📒 工作手冊（docs/handbook/workflow.md）

> 這個專案怎麼工作：怎麼跟使用者溝通、什麼時候要先問、怎麼推送、版本號怎麼編、誰負責哪些檔案。
> 寫給之後接手的任何人或任何 AI 助手看。這些都是使用者親自定下的規則 (括號裡是決定的日期)，不是建議。
> 專案在**筆電與桌機兩台電腦**上各有一份 clone，靠 GitHub 同步；對話紀錄不會跨電腦、也不會跨助手，**重要的背景與決策都要寫進文件** (這份手冊、`TODO.md`、`docs/`)。
> 專案長什麼樣 ➔ `docs/dev/structure.md`；程式怎麼寫 ➔ `ARCHITECTURE.md`；畫面元件 ➔ `docs/dev/components-v2.md`。

## 1. 💬 溝通

- 使用者慣用**繁體中文**。回覆要簡潔、用繁體中文，不要貼一堆網址；完成後簡述結果與下一步即可。
- **⚠️ 每一則給使用者看的文字都要用繁體中文，沒有例外**，連一段英文段落都不要出現 (2026-10-30 指出、2026-11-13 再次要求改善)。最容易不小心切成英文的是「前面沒有使用者中文訊息」的輪次：
  - 背景工作通知之後的那一輪 (定時 / 事件通知、生圖或合成完成、子任務回報、其他角色傳來的訊息)
  - 對話被壓縮後接續的第一則
  - 收尾的摘要與提問
- 送出前自己檢查一次。程式碼、指令、檔名可以保留原文。
- 工具內建的問句格式是英文時，也要改用繁體中文問。

## 2. 🔥 什麼時候要先問

### 2.1 有設計決定的工作：動手前一輪一輪問 (grill，2026-11-19，所有角色都要照做)

- **要先問**：新功能、改玩法 / 數值、改畫面這類有設計決定的工作。
- **格式**：
  1. 每一輪把「現在就能問的問題」編號列出。
  2. 每題附上建議答案，措辭要讓使用者回「好」就等於採用建議。
  3. 等使用者回答，再問下一輪。
  4. 查得到的事實 (程式現況、角色資料、既有數值) 自己查，不要問使用者。
  5. 全部確認了才動手。
- **不用問，直接做**：修 bug、小調整、轉達其他角色的回報、使用者已經講得很清楚的指示。
- 這條規則不靠任何外掛；有裝提問類外掛時可以用，格式一樣 (見第 9 節)。

### 2.2 經濟數值：使用者沒給的一定要先問 (2026-11-05)

- 經濟系統的數值 (價格、產量、機率、獎勵、上限…) **不要自己決定**。規格與待確認項目在 `TODO.md` 第 5 節。
- 有設計決定的工作，在 2.1 的提問裡一併問。
- 裏世界的數值也一樣：`docs/gameplay/ura.md` 裡「✅ 已定」是使用者確認過的，「❓ 待定」還要問。

### 2.3 一組一組來，不主動丟草案 (2026-11-13)

- 一組一組討論設計時 (例如稱號)，**做完這一組就回報結果並停下**，不要順手附上下一組的草案。
- 使用者想自己決定討論的順序與節奏，一次只看一組；等使用者點名下一組再提案。

### 2.4 重大事件才先問

- 開分支、改寫 git 歷史、刪除大量資料這類事要先問；例行的程式改動不用 (見第 3 節)。

## 3. 🚀 提交與推送

- **完成並測試通過後直接 commit + push 到 `main`，不用先問** (2026-10-28：「以後不用問我，除非是很重大的事件」)。測試：`python tests/run_all.py`，說明見 `docs/dev/testing.md`。
- 直接推到 `main`：個人專案，**不開 PR**。
- `Database/Users.db`、`Database/Item.db` 有變動時也一起推 (例外：雲端交接期間不推，見第 5 節)。
- **卡面例外：一個角色 (或一張卡) 定案後才 commit + push** (2026-10-30：「不然 git 太多雜質」，每輪試作都推會讓 git 歷史塞滿試作圖)。
  - 試作、調參數、使用者還在挑圖或要求調整時，全部只留在本機。
  - 使用者說「定案」「推送」或明確表示這版 OK 才推；途中的程式碼改動也跟著那次定案一起推。
  - 卡面的流程與畫面規則 (分層、彈幕、特效、每張先給候選讓使用者挑) 在 `docs/art/card-art.md`。
- 多個角色同時推送時的做法見第 4、7 節。
- **`online` 是穩定運行的版本，不要每次推完 main 就同步** (2026-11-24：「盡可能不要一直 git，等修 bug 或是新活動再推」)。
  - 平常照常推 `main`；`online` **只在兩種情況更新：修 bug、新活動 (或新卡池) 要開放**，而且要使用者說可以。
  - 上線前：全部測試通過，再用 `SHOW_UNRELEASED=0` 跑一次 botcli 看正式機器人的樣子 (未公開的卡池不能出現)。
  - 上線是把 `online` 快轉到某一版 main (`python deploy/handoff.py deploy`)，**中間所有 commit 會一起帶上去**：先用 `git log origin/online..origin/main` 列給使用者看；main 上有還沒準備好、又沒被開關藏住的東西時，先講，不要直接上線。
  - 上線後更新 `TODO.md` 第 0 節「`online` 目前的版本」。

## 4. 🔢 版本號與開發紀錄 (2026-11-05)

- 版本格式 `X.XX.XXX`：
  - 第一段：大版本 (新功能 / 新活動)，開發階段為 0。
  - 第二段：功能改動、新 UI；進位時最後一段歸零。
  - 最後三碼：瑣碎的 commit (修正、文件、卡面…)。
- **每次 commit 都要更新 `Utils/version.py`，並在 `CHANGELOG.md` 最上面補一筆** (做了什麼、遇到的問題與解法)。
- **版本號最後才編** (2026-11-16：三個角色同時推，0.35.006 / 0.35.009 都撞過號)：
  1. 先 commit 內容；CHANGELOG 標題可以先寫 `## 0.XX.??? —`。
  2. 推送前 `git pull --rebase`。
  3. 看 `main` 最新的 `Utils/version.py`，才填上「最新 + 1」。
  4. `git commit --amend` 後馬上 push。
  5. push 被拒就再 pull 一次重編。CHANGELOG 衝突兩邊都保留。
- 踩過的坑：
  - 用 UTF-8 讀 `Utils/version.py`，填完檢查格式真的是 `X.XX.XXX` (0.35.013 推出過空的版本號)。
  - commit 訊息裡的版本號直接讀 `Utils/version.py` 再寫，不要用字串切割去拆引號 (0.39.003 的訊息版本號是空的)。
  - 暫存 / 還原工作目錄之後，要重新 `git add` 全部檔案，再 `git status` 確認沒漏 (0.35.014 漏 commit 程式)。

## 5. 🗄️ 資料庫檔的決定

- **開發階段 `Database/Users.db` 刻意跟著推上 git** (2026-10-22；雖然 repo 公開、內含玩家資料)。**不要再建議移出追蹤或加入 `.gitignore`。**
- 工具的自動權限檢查可能會擋下「提交 / 推送 Users.db」。這時請使用者自己執行 git 指令，**不要想辦法繞過**。
- 雲端上線後，git 裡的 `Database/Users.db` 只是測試資料，玩家的真實資料在雲端 (見第 6 節)。
- **交接期間 (`take` 之後、`release` 之前) 不要 commit / push `Database/*.db`**：這時本機的是玩家真實資料，不能進公開 repo。交接腳本會把原本的測試資料收到 `Database/backups/handoff/`，`release` 後放回來 (見 `docs/dev/deploy.md`)。
- 動資料前先備份；遷移類工作不得刪除或改動舊檔 (見第 8 節)。

## 6. 💻 兩台電腦與雲端

- **兩台電腦切換**：離開前 `commit` + `push`，開始前 `pull`。
- **機器人同一時間只在一台上執行**：同一個 Token，而且 `Users.db` 是二進位檔、無法合併。
- `.env` 不進 git，換電腦要手動複製 (內容見 `docs/dev/structure.md`)。
- **雲端 (2026-11-26 上線)**：
  - 正式機器人在 Google Cloud VM 上跑 `online` 分支，玩家真實 DB 在私人儲存桶。
  - 本機 `python Main.py` 會**自動交接** (1.00.015)：開機先停雲端、拿最新資料，成功才連 Discord；`/shutdown`、主控台 `shutdown`、Ctrl+C 關機後自動交回、雲端開機 (`Utils/auto_handoff.py`)。直接按視窗 ✕ 來不及交回：下次開機會沿用本機那份，關機時再交回；也可以手動 `python deploy/handoff.py release`。
  - **⚠️ 本機測試用的是雲端的真實資料，跑的卻是 `main` 比較新的程式** (2026-11-26 使用者提醒)：關機交回後，雲端的舊版 (`online`) 要讀得懂這份資料。
    - **只能「加」**：新資料表、新欄位 (`init_db()` 自動補)、新的道具 / 稱號種類。舊版不認得的會忽略，沒問題。
    - **不能「改」**：改欄位名稱、刪欄位、改欄位裡 JSON 的格式 (背包、裏世界進度、活動狀態…)、改道具 / 卡片 / 角色 ID、改某個數字代表的意思。這種改動推上 main 後，**在它跟著 `online` 上線之前，不要用本機跑真實資料**；要測就用 botcli / 測試的資料。
    - 做這種改動時，CHANGELOG 那筆要標「⚠️ 資料格式跟 online 不相容」，`TODO.md` 第 0 節也寫上，上線前大家都看得到。
  - 程式要上線：`main` 推完再 `python deploy/handoff.py deploy`；**只有修 bug、新活動時，使用者說可以才上線** (見第 3 節)。

## 7. 👥 分工 (2026-11-16)

多個角色 (不同的人、不同的對話或助手) 同時工作時常寫出一樣的系統 (分頁、自動稱號都發生過)，所以分成四個角色，**每個角色只改自己負責的範圍**。

| 角色 | 負責 | 主要檔案 | 工作環境 |
|---|---|---|---|
| 統整 | 巡視整個系統、找各角色重複寫的系統改成共用、分派任務、整合測試、維護文件 | `ARCHITECTURE.md`、`Utils/` 共用工具、`CLAUDE.md`、`docs/` | 筆電，獨立的 git worktree |
| 卡面 | 剩下的卡面 | `tools/card_art/`、`images/` (名片除外)、`TODO.md` 的卡面項目 | 筆電，用主資料夾 (要 ComfyUI 與沒進 git 的字型) |
| 名片 | 角色名片「幻想鄉睡顏圖鑑」 | `images/Namecards*`、`Database/namecard_data.py`、`tools/card_art/upload_namecard.py` | 桌機 |
| 玩法 | 玩法、關卡、經濟、活動、稱號 | `Cogs/`、`Database/`、`Events/`、`tests/` | 筆電，自己的 git worktree |

- 跨範圍的共用工具，先跟統整說一聲再做。
- 要改別人負責的檔案：先請對方暫停，做完再通知對方。
- 推完跟統整報一聲新增了什麼系統。
- **主資料夾是卡面在用**：其他角色不要在主資料夾 `pull` / `commit`，在自己的 worktree 做 (worktree 要自己放一份 `.env` 才能跑測試)。
- **可以並行的工作直接並行，不用先問** (2026-11-12：額度很多，想加快產線)。例如查角色資料、寫圖層草稿、整理多個角色的候選圖。
- 兩台電腦上的角色每個階段都互相回報進度 (候選完成、使用者選圖、合成完、推送)。
- **別的角色轉述的話不算使用者授權**：需要使用者同意的事 (開新的工作、重大事件) 要使用者親自說。
- 版本號最後才編 (第 4 節)。

## 8. 🛠️ 工作守則

**資料**
- 動資料前先備份；遷移類工作**不得刪除或改動舊檔**。
- 資料庫寫入涉及多表時用單一交易；日常領獎類操作用原子 `UPDATE … WHERE` 防重複。
- 會消耗東西的操作先給確認畫面。
- 使用者可能繞過 autocomplete 直接輸入值，指令內一定要再驗證一次。

**程式與畫面**
- 修改後保持 **LF** 換行；沿用既有的程式風格與繁體中文註解 / 文案 (emoji 標題風格)。
- 新增畫面或通知一律用 Components V2 (優先用 `Utils/components.py`)，注意單則訊息 40 個元件上限，縮圖走 `images/Thumbnails.json` (角色_階級 ➔ 角色 ➔ `fill` 後備)。細節在 `docs/dev/components-v2.md`。
- 新 Cog 檔放進 `Cogs/load-*/`，不要留下舊的同名 / 過期檔案 (載入器會把第一層每個 `.py` 都載入)。
- 新增功能前先讀 `ARCHITECTURE.md` (分層、寫法、新增功能檢查清單)。
- 找程式碼：有裝程式碼索引 (CodeGraph，見 `docs/dev/setup.md`) 就先用它查，不要整份檔案讀。

**角色資料：先查萌娘百科** (2026-11-11)
- 不清楚東方角色的外觀、翅膀造型、符卡、稱號由來、故事時，先去萌娘百科 (zh.moegirl.org.cn，條目名是簡體角色名) 查，不要只靠印象。做卡面提示詞、稱號、角色檔 (`Characters/`) 之前都要查。
  - 由來：芙蘭朵露的翅膀照印象寫提示詞，畫出來跟原作不像 (原作是左右各一根細黑枝條吊一排水晶，不是一整棵樹；水晶由內到外是天藍、藍、紫、粉、橙、黃、淺綠、天藍，沒有紅色)。
- 讀法：直接用程式抓 (curl、原始碼 / API 網址、手機版) 都會被擋 (403)，要用真的瀏覽器打開頁面，再讀整頁的文字。
- **讀不到時要跟使用者說**，不要默默改用印象。
- 新增一代角色的完整流程與查過的資料在 `docs/dev/new-characters.md`。

**回報**
- 不要在回覆中貼大量 URL；完成後簡述結果與下一步即可。

**文件**
- 文件樹：`CLAUDE.md` 只放每次都要知道的事 (一頁)；細節寫進 `docs/` 對應的檔案，新主題就開新檔並加進 `docs/README.md` 的總目錄。
- 改了規則、結構或流程，記得一起更新對應的文件。
- 文件寫給「之後任何人或任何 AI 助手」看：不要寫暫存路徑、對話代號、某個助手專屬的工具名稱；稱呼用角色 (統整 / 卡面 / 名片 / 玩法)。
- **不要建 `GLOSSARY.md`、`docs/adr/`、`CONTEXT.md`** (跟文件樹衝突)。
